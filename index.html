Overview

말로 컨테이너를 관리하되, 실행은 사람이 정한다

BOSUN은 “web 컨테이너 재시작해줘” 같은 자연어로 Docker를 관리하는 서비스입니다. LLM이 어떤 도구를 쓸지 정하고, Docker Agent가 Portainer를 거쳐 Docker를 조작합니다.

팀이 처음에 정한 원칙은 이렇습니다. “LLM은 계획과 명령 파라미터만 만들고, 실제 실행 여부는 코드(정책)와 사용자 승인이 정한다.” 정책은 Agent 안에 있고, 승인은 WEB에서 받습니다. 그래서 WEB은 정책이 “물어봐야 한다”고 판정한 호출을 사람이 읽을 수 있는 카드로 보여 주고, 사람의 결정을 Agent에 정확히 한 번 전달하는 역할을 맡습니다.

Design decisions

Agent 소스를 읽고 정한 것들

Docker Agent API 문서만으로는 승인 흐름의 빈 곳이 보이지 않았습니다. docker-agent 소스(v1.145.0, v1.148.0)를 읽고 확인한 사실마다 파일 이름을 계약서에 근거로 남겼습니다.

브라우저는 WEB 백엔드하고만 통신한다

설계서 1장

Docker Agent API에는 승인 절차를 끄거나 바꾸는 엔드포인트(approve-autonomous, safety-policy, permissions 등)가 있습니다. Agent 스트림의 도구 인자에는 가리지 않은 비밀값도 들어 있습니다. 둘 다 브라우저에 열어 두면 안 되므로 WEB 백엔드(BFF)를 두었습니다.

승인 상태와 만료는 WEB이 들고 있는다

runtime.go Resume · 계약 5장

Agent의 /resume에는 도구 호출 ID가 없고, 기다리는 건이 없어도 200을 주고 결정을 버립니다. Agent는 승인을 무기한 기다립니다.

그래서 WEB이 카드마다 approvalId를 발급하고, 한 번 처리했거나 만료된 카드에는 409를 돌려줍니다. 5분이 지나면 브라우저가 없어도 백엔드가 직접 거부를 보냅니다. 누가 언제 승인했는지도 Agent에는 남지 않아서 WEB이 감사 기록으로 남깁니다.

결정은 approve와 reject만 보낸다

session_manager.go ResumeSession

approve-tool이나 approve-autonomous는 세션 권한을 넓혀서 그 뒤 호출을 묻지 않고 실행합니다. 카드 한 장의 승인이 이후 호출까지 열면 안 되므로 쓰지 않습니다. 같은 이유로 세션 권한 API도 막았습니다. 세션 규칙이 agent.yaml보다 먼저 적용돼 정책의 거부 규칙까지 뚫기 때문입니다.

승인 카드는 LLM이 아니라 코드 템플릿이 쓴다

server/tools.ts · 계약 6장

Agent의 승인 요청에는 대상, 위험도, 설명이 없습니다. LLM에게 요약을 맡기면 승인할 내용을 LLM이 다시 쓰게 됩니다. 그래서 도구 요청(DELETE /containers/nginx-web 같은 method·path·본문)을 표에 맞춰 카드로 바꿉니다.

컨테이너 생성은 본문에서 이미지, 명령, 포트, 마운트, privileged, 호스트 공유를 꺼내 보여 줍니다. 10월 11일 실제 모델이 생성 명령에 셸 명령을 넣는 것을 보고, exec를 정책으로 막더라도 카드에서 명령은 보여야 한다고 판단했습니다.

비밀값은 “보여 줄 필드만 고르는” 방식으로 가린다

계약 5장 4항 · server/mask.ts

가릴 값을 찾는 방식은 새 형식이 나오면 놓칩니다. 카드에는 도구별로 고른 필드만 싣고, 처리 과정에는 인자를 아예 보내지 않습니다. 모델이 답에 옮겨 적을 수 있는 토큰·키 형식은 한 번 더 가립니다.

Implementation

화면과 백엔드

스트림 이어붙이기

승인을 기다리는 동안 Agent 연결은 끊지 않는다

  • Agent가 승인을 요청하면 브라우저로 가는 스트림은 승인 카드에서 끝내고, Agent 쪽 스트림은 백엔드가 열어 둔 채 기다립니다.
  • 승인이나 거부가 오면 /resume으로 전달하고, 그 요청의 응답으로 Agent 스트림의 나머지를 이어서 보냅니다.
  • 카드에는 위험도(되돌릴 수 없음, 잠깐 끊김, 새로 만듦), 승인하면 생기는 일, 접힌 기술 정보가 있습니다. 64자리 ID 대신 앞서 조회한 이름을 보여 줍니다.
승인과 차단은 다른 모양으로

버튼이 있는 카드와 버튼이 없는 안내

  • 정책이 “묻기”로 판정하면 버튼이 있는 승인 카드, “거부”로 판정하면 버튼 없는 차단 안내입니다. 차단은 승인해도 실행할 수 없는 작업이라 버튼을 두지 않습니다.
  • 정책 차단은 Agent 스트림에 도구 오류로 섞여 옵니다. 오류 문구의 맨 앞만 맞춰 보고 차단을 가려냅니다. 도구 결과에는 컨테이너 이름이나 로그 같은 외부 문자열이 섞이기 때문입니다.
  • 훅이 적은 사유의 첫 문장을 가린 뒤 보여 주고, 꼭 필요한 작업이면 Portainer 화면에서 직접 하라고 링크를 붙입니다.
대화별 동시 처리

동시 처리를 열자 생긴 문제까지 막기

  • 처음에는 백엔드 전체에서 Agent 스트림을 하나만 열었습니다. Agent 소스(dispatcher.go)에서 승인 요청이 세션마다 하나씩 온다는 것을 확인하고, v0.4.0에서 턴을 대화마다 나눴습니다(기본 3개 동시).
  • 턴마다 브라우저로 보낸 이벤트를 모아 두어서, 처리 중에 새로고침해도 다시 붙어 처음부터 받습니다. 처리 중인 작업은 멈출 수 있습니다.
  • 대화가 여럿이면 같은 컨테이너를 서로 다른 카드가 기다릴 수 있습니다. 한쪽이 먼저 지우고 같은 이름으로 새로 만들면, 나중 승인은 사용자가 본 것과 다른 대상을 바꿉니다. 같은 대상을 기다리는 카드에는 경고를 붙이고, 카드가 뜬 뒤 다른 대화가 같은 대상을 승인했으면 실행하지 않고 거부로 돌립니다(TARGET_CHANGED).
정책은 Agent 설정 한 곳에

정책은 웹에서 옮기고, 저장하면 Agent가 다시 뜬다

  • WEB은 세션을 만들 때 안전 모드를 보내지 않습니다. 그래야 agent.yaml에 적힌 정책이 그대로 적용됩니다.
  • 설정의 정책 보드에서 작업을 허용·묻기·거부 세 칸 사이로 옮깁니다. 저장하면 agent.yaml의 permissions에 쓰고 Agent를 다시 띄웁니다. 변경 작업을 허용 칸으로 옮길 때는 한 번 더 확인을 받고, 허용 칸에서 실행된 변경도 감사 기록에 남깁니다.
  • 그 밖에 대화 이름·고정·찾기·내보내기, 메시지 고쳐 다시 보내기, 승인 기록, 삭제 전 백업 목록, 토큰 사용량, 대화창에서 모델 고르기, API 키 상태와 남은 크레딧 보기가 있습니다.

Findings

실제로 붙여 보고 찾은 것

컨테이너 안의 Agent가 Portainer에 붙지 않았다 (11월 12–15일)

증상
Portainer API가 계속 303을 돌려줬습니다.
첫 가설
HTTP 포트가 HTTPS로 넘긴다고 보고 내부 주소를 HTTPS로 바꿨지만 같은 303이 났습니다. 가설이 틀린 것을 확인하고 응답 헤더를 직접 봤습니다.
원인
헤더에 Redirect-Reason: AdminInitTimeout이 있었습니다. Portainer는 첫 실행 후 5분 안에 관리자 계정이 없으면 API를 막습니다. 이를 풀자 이번에는 빈 키로 인증 오류가 났는데, docker-agent 소스를 따라가 보니 환경변수의 빈 값도 “찾은 값”으로 쓰고 있었습니다.
해결
설치 안내에 5분 제한과 복구 방법을 적고, Agent를 띄울 때 빈 값을 지워 “값 없음”이 바로 드러나게 했습니다. Portainer는 사용자가 이미 쓰는 것에 붙이도록 설치 구성에서 뺐습니다.

승인을 5분 기다리면 연결이 300초에 끊긴다

증상
승인 대기나 오래 걸리는 도구 실행 중에 WEB 백엔드와 Agent 사이 연결이 끊겼고, Agent는 요청이 끊기면 실행을 취소했습니다.
원인
Node fetch(undici)는 응답 본문이 300초 동안 오지 않으면 연결을 끊습니다(UND_ERR_BODY_TIMEOUT). Agent는 승인을 기다리는 동안 keepalive를 보내지 않습니다. 10월 9일 실측으로 확인했습니다.
해결
Agent 스트림만 기본 타임아웃이 없는 node:http로 엽니다. 구간마다 “바깥 구간이 안쪽보다 길어야 한다”는 규칙으로 타임아웃 표를 만들었고, 리버스 프록시에 끊기지 않게 브라우저 쪽에는 15초마다 ping을 보냅니다.

Agent가 조용히 멈추는 경우들

반복 한도
반복 한도(max_iterations)에 닿으면 Agent는 계속할지 묻고 기다리는데, WEB에는 그 화면이 없습니다. 백엔드가 바로 거부를 보내 멈추게 했습니다.
대화 제목
제목이 없으면 Agent가 영어 프롬프트로 LLM을 한 번 더 불러 제목을 만들었고, 영어나 빈 제목이 나왔습니다. 첫 메시지로 WEB이 제목을 정해 그 호출을 없앴습니다.
훅 순서
v1.148.0 소스를 다시 읽어 훅이 모두 사용자 승인 전에 불린다는 것을 확인했습니다. 삭제 전 백업은 거부해도 남고, 백업 훅이 allow를 돌려주면 승인 카드 없이 바로 실행됩니다. Agent 담당 팀원에게 훅 위치와 반환값을 정리해 전달했습니다.

실제 Portainer 연동에서 나온 정책 문제

정책 훅은 Agent 담당 팀원의 코드입니다. 10월 11일과 13일 실제 연동에서 정책이 막아야 할 요청을 직접 보내 보고, 찾은 문제를 계약서에 적어 전달했습니다.

문제원인상태
경로를 arch%69ve처럼 인코딩하면 파일 읽기 거부 규칙을 피함 정책은 글자 그대로 비교하는데 Portainer는 %XX를 풀어서 처리 반영됨
허용 목록 방식으로 바꾸고 %, .. 등이 든 경로는 거부
이미지 tar 내보내기(GET /images/{name}/get)가 승인 없이 실행됨 거부 목록에 없는 경로는 통과 반영됨
거부 규칙과 허용 목록 양쪽에서 거부
Windows에서 한글 인젝션 차단 규칙이 동작하지 않음 훅 Python이 입력을 CP949로 읽음 반영됨
python -X utf8로 실행
막은 메시지가 대화 기록에 남아 다음 턴에 모델이 답함 차단은 그 턴만 멈추고 기록은 그대로 반영됨
모델에 보내기 전에 안내 문구로 바꾸는 훅 추가
force=y로 보내면 실행 중인 컨테이너가 강제 삭제됨 Docker는 ""/0/no/false/none만 거짓인데 훅은 1/true/yes/on만 참으로 봄 반영됨
훅도 Docker처럼 빈 값·0/no/false/none만 거짓으로 봄. WEB 카드의 강제 삭제 표시도 Docker 기준

실제 Agent 리허설(10월 27~28일)

상황
실제 docker-agent, Portainer, 모델로 v0.4.0 기능 전체를 써 봤습니다.
찾은 것
모델이 아무것도 내지 않고 끝나 화면이 멈춘 것처럼 보임. 모델이 도구 호출을 글로 써서 보냄. Agent가 같은 호출 반복을 감지해 멈춤. 생성 요청 본문이 빠져 두 번 막혔는데 화면에는 공통 문구만 나와 이유를 알 수 없음.
결과
WEB 0.5.0~0.5.2로 고쳤습니다. 세 경우를 각각 오류 코드와 다시 시도 안내로 나누고, 차단 안내에 사유와 Portainer 링크를 붙이고, 승인 카드에 위험도를 달았습니다. 같은 상황을 가짜 Agent 시나리오와 테스트에도 넣었습니다.
Interface

구조가 바뀌어도 화면은 버틴다

처음 설계(계약 v0.2)는 Agent와 Portainer 사이에 승인 게이트웨이 Airlock을 두고, Airlock이 WEB에 webhook으로 승인을 요청하는 구조였습니다. 10월 8일 팀이 Airlock을 일단 빼고 Docker Agent 자체 승인을 쓰기로 정했고, 다음 날 계약 v0.3.0으로 바꿨습니다.

승인 요청이 오는 곳(webhook → Agent 스트림)과 결정을 보내는 곳(Airlock API → /resume)이 모두 바뀌었지만, 브라우저 ↔ WEB 백엔드 형식은 그대로 두었습니다. 화면은 AgentClient 인터페이스만 보도록 나눠 두었기 때문에, 그 커밋에서 화면 코드는 승인 뒤 단계 표시 몇 줄과 목업 조정만 바뀌었고, 나머지는 백엔드와 가짜 Agent였습니다.

계약서는 v0.1(9월 24일)부터 v0.5.3(10월 29일)까지 31개 버전을 냈습니다. 9월 28일 하루에만 원문과 다시 대조하며 v0.2부터 v0.2.7까지 여덟 판을 냈습니다. 팀원에게 묻기 전에 확인할 수 있는 것은 소스로 먼저 확인하고, 다른 파트의 결정이 필요한 일은 계약서 7장 한 곳에 누구에게 무엇이 필요한지와 함께 적습니다.

기술 선택과 이유

React 19 + TypeScript + Vite계속 바뀌는 메시지 상태를 컴포넌트로 나누고, 이벤트 형식을 타입으로 고정Next.js는 쓰지 않음. 내 PC에서 여는 관리 도구라 SEO·서버 렌더링이 필요 없음
Tailwind CSS v4상태별로 조금씩 다른 작은 컴포넌트가 많음컴포넌트 라이브러리는 쓰지 않음. 핵심인 승인 카드가 이 프로젝트에만 있는 화면
SSE (POST + fetch)응답은 서버에서 브라우저로 한 방향이고, Docker Agent도 SSEWebSocket은 쓰지 않음. 승인 버튼은 POST 한 번이면 됨
Node 22 + Hono + node:sqlite화면과 이벤트 타입 파일을 같이 쓰고, Node가 타입만 지우고 바로 실행해 빌드 단계가 없음FastAPI는 쓰지 않음. 타입을 두 언어로 따로 맞춰야 함
채팅 템플릿 없이 직접 조립승인(버튼 있음)과 차단(버튼 없음)의 분기가 핵심open-webui는 Docker Agent에 붙이는 방식에 대화 안 승인 통로가 없음
Docker 올인원 이미지웹과 Agent를 한 이미지로 묶어 docker compose up 한 번으로 실행Portainer는 넣지 않음. 사용자가 이미 쓰는 Portainer에 붙이는 것이 실제 사용 흐름
